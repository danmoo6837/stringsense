# 기타 음원 전사 성능 평가 및 개선 내역

작성일: 2026-11-04

## 1. 평가 목적과 실행 방식

기타 음원을 분석해 생성한 MIDI의 음높이, 음 시작 시각, 종료 시각이 정답과 얼마나 일치하는지 측정했다. 평가 대상은 현재 서비스의 librosa 기반 백엔드다.

평가기는 전사 함수를 직접 호출하지 않고 다음 경로로 실행한다.

```text
샘플 WAV → 실제 POST /analyze → MIDI 생성
         → 응답의 midi_url에서 MIDI 다운로드
         → 정답 JAMS와 일대일 매칭 → 곡별·전체 점수 저장
```

Windows에서는 librosa 내부 Numba의 캐시 생성이 권한 제한에 걸려 실행이 지연됐다. 완료된 성능 측정은 모두 Docker의 Linux/Python 3.11 환경에서 수행했다. 중단된 Windows 실행은 최종 점수에 포함하지 않았다.

## 2. 데이터 구성

GuitarSet 마이크 음원 360개와 대응하는 JAMS 정답 360개를 사용했다. 파일명 기준으로 누락된 짝은 없었다.

```text
backend/data/inputs/
├─ annotation/              # 정답 JAMS 360개
└─ audio_mono-mic/
   ├─ solo/                 # 솔로 음원 180개
   └─ comp/                 # 반주 음원 180개
```

음원은 최초 전체 평가 후 solo/comp 폴더로 분리했으며 파일명과 내용은 유지했다. 평가기는 하위 폴더까지 탐색하고 `--group solo`로 솔로만 선택할 수 있도록 변경했다.

JAMS의 `note_midi`에서 `time`을 시작 시각, `time + duration`을 종료 시각, `value`를 음높이로 읽는다. 줄별 주석을 모아 비교하되 음높이 소수값은 반올림하지 않는다.

- 전체 정답 음표: 62,476개
- solo 정답 음표: 16,861개
- comp 정답 음표: 45,615개
- 음원 길이: 14.4~45.7076초. 백엔드의 60초 제한에 의해 잘리는 샘플은 없음.

## 3. 평가 기준

mir_eval 0.8.2의 일대일 음표 매칭을 사용했다. 하나의 정답 음을 여러 검출 음이 중복해서 맞혔다고 인정하지 않는다.

| 항목 | 기준 |
|---|---|
| 음 시작 시각 | 정답에서 ±50ms 이내 |
| 음높이 | 정답에서 ±50센트 이내 |
| 종료 시각 포함 평가 | 위 조건에 추가로 종료 오차가 정답 길이의 20% 또는 50ms 중 큰 값 이내 |
| 정밀도 | 맞힌 음 / 검출한 음 |
| 재현율 | 맞힌 음 / 정답 음 |
| F1 | 정밀도와 재현율의 조화평균 |

본문 기본 수치는 모든 음표 수를 합산한 micro 지표다. macro F1은 곡별 F1을 동일 비중으로 평균한 별도 지표다. JSON/CSV의 점수는 0~1이며 표에서는 백분율로 표시한다.

PDF에 사용하는 임시 120 BPM·4/4는 평가에 사용하지 않았다. 정답 시간 이동이나 음높이 보정도 적용하지 않았다.

## 4. 평가 이력

### 4.1 최초 전체 평가

실제 API로 전체 360곡을 처리했으며 성공 360곡, 실패 0곡이었다.

| 대상 | 곡 수 | 정밀도 | 재현율 | 시작+음높이 F1 | 종료 포함 F1 |
|---|---:|---:|---:|---:|---:|
| 전체 | 360 | 29.72% | 10.63% | 15.66% | 5.83% |
| solo | 180 | 41.58% | 27.18% | 32.87% | 13.94% |
| comp | 180 | 18.18% | 4.52% | 7.24% | 1.85% |

전체 정답 62,476개 중 검출 22,353개, 매칭 6,643개, 오검출 15,710개, 매칭되지 않은 정답 55,833개였다.

### 4.2 폴더 분리 후 solo 전용 재평가

solo/comp 폴더를 나누고 solo 180곡만 API로 다시 평가했다. 성공 180곡, 실패 0곡이며 이전 전체 평가의 solo 집계와 동일했다.

- 정밀도 41.58%, 재현율 27.18%, F1 32.87%
- 종료 포함 F1 13.94%
- 정답 16,861개, 검출 11,023개, 매칭 4,583개
- 오검출 6,440개, 매칭되지 않은 정답 12,278개

여기서 매칭되지 않은 정답은 실제 검출 누락 외에 시작 시각이나 음높이가 허용 범위를 벗어난 경우도 포함한다.

## 5. 오류 원인 진단

저장된 개선 전 solo 검출 결과에서 시작 시각 허용 범위만 바꾸어 다시 채점했다. 음높이 허용 범위는 ±50센트로 유지했다.

| 시작 허용 오차 | F1 |
|---|---:|
| ±50ms | 32.87% |
| ±100ms | 50.39% |
| ±200ms | 60.69% |

허용 범위를 넓히자 점수가 크게 올라 시작 시각 오차가 성능 저하에 기여함을 확인했다. 이는 진단용 재채점이며 알고리즘 개선 결과가 아니다. 개선 전후 본 평가에서는 ±50ms를 유지했다.

코드에서는 빠른 공격점을 제거하는 140ms 최소 간격, 반복음을 합치는 처리, CQT 계산/주파수 해석 기준 불일치, 다음 음 시작을 기준으로 종료를 정하는 처리도 확인했다.

## 6. 실제 코드 변경 내용

변경 파일: `backend/app/services/transcribe.py`

### 6.1 전사 엔진을 librosa로 통일

기존에는 Basic Pitch를 먼저 실행하고 결과가 없으면 librosa로 넘어갔다. 요청에 따라 Basic Pitch 호출과 파싱 코드를 제거하고 `requirements.txt`에서도 의존성을 제거했다. `pipeline.py`는 전처리한 오디오와 샘플레이트를 librosa 전사 함수에 전달한다. 완료된 위 평가들은 모두 librosa 단일 전사 기준이다.

### 6.2 음 시작 시각 검출 조정

| 설정 | 변경 전 | 변경 후 | 목적 |
|---|---|---|---|
| `backtrack` | `True` | `False` | 검출 시점을 앞쪽 에너지 최소점으로 되돌리는 동작 해제 |
| `delta` | 0.12 | 0.07 | 약한 공격점도 검출하도록 민감도 증가 |
| `wait` | 3 | 1 | 연속 공격점의 검출 대기 간격 축소 |
| 최소 onset 간격 | 140ms | 50ms | 빠른 음들이 제거되는 현상 완화 |
| 최소 음 길이 | 60ms | 40ms | 짧게 연주한 음 보존 |

평가 코드의 허용 오차 설정과 검출기의 민감도 설정은 별개다. 평가 오차는 `--onset-ms`, `--pitch-cents`로 선택할 수 있으며 이번 비교에서는 기본값을 사용했다.

### 6.3 반복음 보존

변경 전에는 같은 음높이의 음이 가까이 있으면 `_merge_repeated_notes()`로 합쳤다. 재차 피킹한 음도 하나가 될 수 있어, librosa 추출 결과를 반환할 때 이 병합 함수를 호출하지 않도록 바꿨다. 서로 다른 시작점으로 검출된 같은 음높이를 별도 음표로 유지한다.

### 6.4 CQT 음높이 해석 기준 수정

기존 CQT 계산은 `fmin`을 지정하지 않아 라이브러리 기본 기준을 사용했지만, 결과 주파수 배열은 C2 기준으로 만들고 있었다. 두 기준이 다르면 CQT 대체 경로에서 음높이를 잘못 해석할 수 있다.

변경 후에는 `fmin = librosa.note_to_hz("C2")`를 한 번 정하고 CQT 계산과 주파수 배열 생성 양쪽에 동일하게 전달한다.

### 6.5 pYIN 대표 음높이 선택 변경

변경 전에는 유효한 F0 주파수들의 중앙값을 음높이로 바꿨다. 변경 후에는 각 프레임을 MIDI 음높이로 변환하고, pYIN 신뢰도 합계가 가장 큰 음높이를 대표값으로 선택한다. 서로 다른 음높이 사이의 중앙값이 대표 음이 되는 현상을 줄이기 위한 처리다.

### 6.6 종료 시각 추정 변경

변경 전에는 다음 onset 또는 최대 1.25초를 종료 기준으로 사용했고, 마지막 음은 기본 0.5초로 처리했다.

변경 후에는 다음 onset을 종료 상한으로 두고, 검출한 음높이에 가장 가까운 CQT 주파수 빈의 에너지를 추적한다. 구간 내 최대 에너지의 15% 아래로 3프레임 연속 내려가면 그 지점을 종료로 선택한다. 최소 음 길이 조건을 만족해야 하며, 해당 감소가 없으면 다음 onset을 사용한다. 마지막 음은 분석한 오디오 끝까지 추적한다.

이 방식은 에너지 기반 초기 추정이다. 겹치는 음이나 긴 잔향의 실제 종료를 완전히 복원하는 방식은 아니며, 다음 onset을 넘는 음 길이도 현재 표현하지 않는다.

동일 음원 180곡을 변경된 Docker 백엔드 API에서 다시 처리했다. 성공 180곡, 실패 0곡이었다.

| 재현율 | 27.18% | 76.04% | +48.86%p |

## 8. 검증 범위와 남은 과제

- 전사 회귀 테스트 3개를 Docker에서 통과했다. 빠른 공격점 보존과 신뢰도 기반 대표 음높이 선택을 확인했다.
- 여러 변경을 함께 적용했으므로 개별 변경이 몇 %p의 개선을 만들었는지는 측정하지 않았다.
- 개선 후 comp 180곡 및 전체 360곡 재평가는 아직 수행하지 않았다. 69.90%는 solo 전용 점수다.
- 오류 분석에 사용한 동일 데이터셋으로 재평가했으므로 독립 테스트셋의 일반화 성능으로 해석하지 않는다.
- 줄·프렛 배치, PDF 조판 정확도는 이번 평가 범위에 포함하지 않는다.
- 다음 과제는 오검출 억제, 잔향/겹친 음의 종료 추정, comp 재평가 및 별도 녹음 데이터 검증이다.

## 9. 코드와 실행 방법

| 파일 | 역할 |
|---|---|
| `backend/evaluate.py` | 파일 대응, 실제 API 호출, MIDI 비교, 집계와 저장 |
| `backend/app/services/transcribe.py` | librosa 전사 알고리즘 |
| `backend/app/services/pipeline.py` | 전처리·전사·TAB/MIDI/PDF 생성 연결 |
| `Dockerfile`, `compose.yaml` | 백엔드와 평가 실행 환경 |
| `requirements-eval.txt` | mir_eval 평가 의존성 |

```bash
# 백엔드 빌드 및 실행
docker compose up -d --build backend

# solo 전용 평가
docker compose --profile evaluation run --rm evaluate python backend/evaluate.py --base-url http://backend:8000 --group solo

# 전체 평가
docker compose --profile evaluation run --rm evaluate
```

평가 실행마다 새 결과 폴더를 만든다. `summary.json`은 집계, `tracks.csv`는 곡별 점수, 곡별 `.mid`는 실제 API 결과, 곡별 `.json`은 정답·검출 음표와 점수를 담는다.

## 11. 개선 후 시작 허용 오차 100ms·200ms 추가 평가

개선 후 실제 API 결과인 `20261104T101928149565Z`의 solo 180곡을 재채점했다. 전사 결과는 그대로 두고 시작 시각 허용 범위만 변경했다. 음높이 ±50센트, 종료 허용 오차(정답 길이 20% 또는 50ms 중 큰 값)는 유지했다. 50ms 재계산이 기존 집계와 정확히 일치하는 것도 확인했다.

| 시작 허용 오차 | micro 정밀도 | micro 재현율 | micro F1 | 종료 포함 micro F1 |
|---|---:|---:|---:|---:|
| ±50ms | 64.68% | 76.04% | 69.90% | 50.55% |
| ±100ms | 66.30% | 77.94% | 71.65% | 51.90% |
| ±200ms | 67.62% | 79.49% | 73.07% | 53.48% |

시작+음높이 매칭 음표 수는 각각 12,821개, 13,141개, 13,403개다. macro F1은 각각 70.28%, 72.04%, 73.40%이며, 종료 포함 macro F1은 50.92%, 52.29%, 53.78%다.

허용 범위 확대에 따른 점수 상승이며 새로운 알고리즘 개선은 아니다. 개선 전에는 50ms→200ms 확대 시 F1이 32.87%→60.69%였지만, 개선 후에는 69.90%→73.07%로 차이가 줄었다. 이는 이번 데이터에서 시작 시각 오차에 의한 점수 손실이 줄었음을 보여준다.

결과 파일은 개선 후 실행 폴더의 `onset_tolerance_summary.json`과 `onset_tolerance_tracks.csv`에 저장했다. 곡별 CSV는 180곡 × 3가지 허용 오차 × 2가지 지표로 구성된다.

재현 명령:

```bash
python backend/rescore.py backend/data/evaluations/20261104T101928149565Z
```

## 12. 시작·종료를 동시에 고정 허용 오차로 평가

같은 개선 후 solo 180곡 결과를 시작·종료 모두 고정 ±50ms, ±100ms, ±200ms로 재채점했다. 음높이는 ±50센트를 유지했다. 이번 종료 조건은 기존의 `max(음 길이 20%, 50ms)` 대신 고정 시간만 사용한다. 따라서 아래 50ms 종료 포함 F1은 기존 50.55%와 평가 조건이 다르다.

| 시작 허용 오차 | 종료 허용 오차 | 정밀도 | 재현율 | 시작+음높이+종료 micro F1 |
|---|---|---:|---:|---:|
| ±50ms | ±50ms | 44.25% | 52.02% | 47.82% |
| ±100ms | ±100ms | 57.73% | 67.87% | 62.39% |
| ±200ms | ±200ms | 62.89% | 73.93% | 67.97% |

매칭 음표 수는 각각 8,771개, 11,444개, 12,466개다. macro F1은 48.01%, 62.55%, 67.89%다. 허용 범위 변경에 따른 결과이며 추가 전사 개선을 의미하지 않는다.

## 14. Basic Pitch 포함·개선 전 코드 재구성 평가 (2026-11-05 KST)

요청에 따라 Basic Pitch 우선 실행을 포함하고, 대체 librosa를 4.2 당시 개선 전 설정으로 복원한 평가용 스냅샷을 별도 실행했다. 스냅샷은 `backend/benchmarks/transcribe_legacy.py`이며 `compose.legacy.yaml`로 서비스와 분리한 실제 백엔드 API에서 solo 180곡을 평가했다. Git 커밋 전체 복원이 아니라 대화에 기록된 전사 알고리즘의 재구성이며 Docker 의존성은 Basic Pitch 0.4.0을 설치한 현재 이미지와 동일하다.

복원 항목: 최소 음 길이 60ms, onset 간격 140ms, backtrack=True, delta=0.12, wait=3, 반복음 병합, F0 중앙값, 개선 전 CQT 기준 불일치, 다음 onset/최대 1.25초 기반 종료 및 마지막 음 0.5초 처리. Basic Pitch의 기존 60ms 필터와 반복음 병합도 유지했다.

| 버전 | 정밀도 | 재현율 | 시작+음높이 F1 | 종료 포함 F1 |
|---|---:|---:|---:|---:|
| 4.2 개선 전 librosa 단독 | 41.58% | 27.18% | 32.87% | 13.94% |
| Basic Pitch 포함·개선 전 대체 코드 | 78.05% | 74.21% | 76.08% | 56.38% |
| Basic Pitch 포함·개선형 대체 코드 | 78.05% | 74.21% | 76.08% | 56.38% |

시작 ±50ms, 음높이 ±50센트, 종료는 기존 길이 비례 기준이다. 성공 180곡, 실패 0곡. 정답 16,861개, 검출 16,033개, 매칭 12,513개, 오검출 3,520개, 매칭되지 않은 정답 4,348개.

이전 Basic Pitch 우선 실행의 곡별 검출 음표와 비교해 180곡 모두 완전히 동일함을 확인했다. 따라서 이번 샘플에서는 대체 librosa 개선 여부가 최종 결과를 바꾸지 않았다. API에 사용 엔진을 기록하지 않으므로 이 비교만으로 곡별 경로 사용 여부까지 단정하지는 않는다.

결과: `backend/data/evaluations/20261104T163410425375Z/`.
